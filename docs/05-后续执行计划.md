# 后续执行计划

## 1. 职责

本文档只做一件事：

```txt
把未完成功能从“按单个 task 推进”改成“按业务批次推进”。
```

这里不写按钮、字段、接口细节；那些内容继续放在 `features/` 和 `tasks/`。

## 2. 为什么要改

当前文档体系已经能支撑单功能稳定开工，但后续剩余任务很多，如果继续一项项复核，会出现下面的问题：

```txt
1. 同一业务链被拆成很多小 task，重复读文档、重复确认、重复写进度。
2. 同一页面或同一数据链路被多次打开，效率低，token 消耗高。
3. 一些本来应该整体设计的模块被切碎，容易局部对齐、整体失衡。
4. 高风险能力和低风险界面能力混在同一个推进节奏里，不够经济。
```

所以后续执行改为：

```txt
按业务批次复核
按业务批次确认
按业务批次实现
按业务批次验证
```

## 3. 执行原则

### 3.1 总原则

```txt
1. 不再按单个 F-xxx-xxx 零碎推进。
2. 一个批次只做一次统一复核，不对每个小功能重复复核。
3. 一个批次只集中整理一次确认点，不反复单点打断。
4. 一个批次确认后，连续实现，再统一做 verify/typecheck/build。
5. 高风险能力仍然保留确认；低风险列表、入口、只读展示尽量并批处理。
```

### 3.2 风险分级

| 等级 | 含义 | 处理方式 |
|---|---|---|
| 低 | 入口、列表、只读信息、普通界面组织 | 可以按批直接推进 |
| 中 | 普通 CRUD、表单、筛选分页、上下文切换 | 批次内统一复核后推进 |
| 高 | 删除影响大、写文件、模型调用、任务状态、导出、长流程编排 | 批次开工前必须集中确认 |

### 3.3 文档规则

```txt
1. 现有 docs/tasks/ 单功能文档不删，继续保留作事实来源。
2. 后续新增“批次计划文档”，用于覆盖一组相关 task 的统一执行方案。
3. 03 继续记录当前主线，但主线单位从“单 task”改成“批次”。
4. 如果某个单功能 task 明显不够用，再在对应批次文档里统一补，不再零散补。
```

## 4. 批次划分

### P1 设置收尾批

```txt

  F-002-015 关于与版本信息

目标：
  收口 M-002 设置模块剩余能力。

为什么合并：
  同属设置页，同一入口、同一信息架构、同一类 preload/main/settings IPC。

风险等级：
  中

集中确认：
  需要

主要风险：
  1. 开发者能力的生产环境暴露边界
  2. 版本检查和下载能力的策略边界
```

```txt
目标：

主要风险：
```

```txt

风险等级：
  高

集中确认：
  必须

主要风险：
  1. 时间线数据来源不能依赖临时界面态
```

### P11 真实数据验收批

```txt
包含：
  P5 到 P10 主业务链路真实数据走查

目标：
  不再继续靠结构验证判断完成度，用真实项目、真实模型配置、真实媒体和真实导出结果验证主链路。

为什么合并：
  原文、剧本、资产、生产和导出是一条连续链路，拆开验收会漏掉跨模块数据关系。

风险等级：
  高

集中确认：
  需要真实数据和真实模型配置；缺失时记录阻塞，不写假数据。

主要风险：
  1. 文本、图片、视频模型真实调用能力不足
  2. 图片/视频生成执行器和任务中心状态不闭环
  3. P10 草稿包素材校验和剪映原生 schema 边界被误判
```

## 5. 推荐执行顺序

| 顺序 | 批次 | 说明 |
|---|---|---|
| 1 | P1 设置收尾批 | 先结束设置模块，避免后续继续穿插设置改动 |
| 2 | P2 应用壳批 | 统一应用入口、菜单、欢迎和版本壳 |
| 3 | P3 项目管理批 | 建立项目主上下文 |
| 4 | P4 任务中心批 | 建立统一可观测能力 |
| 5 | P5 原文输入批 | 打通内容输入链 |
| 6 | P6 剧本 Agent 批 | 打通剧本生成链 |
| 7 | P7 剧本结果批 | 收口剧本结果管理 |
| 8 | P8 资产生产前置批 | 打通资产与角景复用链 |
| 9 | P9 生产工作台批 | 完成主生产工作台 |
| 10 | P10 导出批 | 最后做导出收口 |
| 11 | P11 真实数据验收批 | 用真实项目走查 P5-P10，整理阻塞和后置增强 |

## 6. 每批固定执行步骤

后续每个批次都按同一套路执行：

```txt
1. 新建或优化一个批次计划文档。
2. 统一复核该批次涉及的 features、tasks、参考源码和当前实现。
3. 把需要确认的点集中列出来，一次性确认。
4. 用户确认后连续实现。
5. 批次完成后统一执行专项 verify、typecheck、必要回归、build。
6. 最后更新 03、04，以及该批次相关 task 执行后记录。
```

## 7. 现有单功能 task 怎么处理

```txt
1. 已有单功能 task 不删除。
2. 后续批次文档作为“执行入口”，单功能 task 作为“事实和细节来源”。
3. 如果单功能 task 已足够清楚，批次文档只引用，不重复抄写。
4. 如果多个单功能 task 之间边界不合理，在批次文档里重写合并口径。
```
