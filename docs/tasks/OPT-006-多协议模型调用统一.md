# OPT-006 多协议模型调用统一

状态：已完成

## 0. 快速理解

一句话：把文本、图片、视频、TTS 的模型调用先收口到同一套“模型调用网关”，不让业务页面、业务 service、adapter 各自写一套调用规则。

为什么现在做：后面图片、视频、TTS、ComfyUI、OpenAI Compatible、自定义 adapter 都会继续增加。如果没有统一入口，错误码、日志、任务中心、测试入口会越写越散。

做完后有什么用：不管是 SDK 模型、OpenAI Compatible、内置 adapter，还是参考项目自定义 adapter，调用前都能统一解析供应商/模型/能力，调用中统一记录 requestId、协议、耗时，失败时统一转成可理解的模型错误。

这一步不碰什么：不做 adapter 沙盒安全，不做 allowlist，不做取消/超时/重试，不做 ComfyUI workflow 节点映射，不改普通模型连接主数据。

## 1. 本次做什么

1. 新增模型调用网关：
   - 统一 `requestId`
   - 统一 `vendorId`
   - 统一 `modelName`
   - 统一 `modelType`
   - 统一 `protocol`
   - 统一开始/成功/失败日志
2. 统一协议识别：
   - 官方 SDK：OpenAI、DeepSeek、Anthropic、Gemini 等内置文本供应商。
   - OpenAI Compatible：AtlasCloud、火山、MiniMax，以及 OpenAI 自定义 Base URL。
   - builtin adapter：内置供应商但媒体能力未实现时明确提示。
   - custom adapter：高级 adapter 脚本和普通连接投影复用 adapter。
   - ComfyUI workflow：先识别为 workflow 协议，但真实 workflow 执行仍留给 `OPT-033`。
3. 文本调用接入网关：
   - `invokeText`
   - `streamModelText`
4. 媒体调用接入网关：
   - `generateImageByModel`
   - `generateVideoByModel`
   - `generateAudioByModel`
5. 模型测试继续走同一入口，不新增页面 SDK import。
6. 失败归一：
   - 已经是 `VtError` 的错误保留状态码。
   - 第三方 SDK/adapter 原始错误包装成 `MODEL_ERROR`。
   - 错误 detail 写日志，不直接暴露密钥、完整路径和 stack 给页面。
7. 增加专项 verify：
   - 确认网关文件存在。
   - 确认文本/图片/视频/TTS 都调用网关。
   - 确认 renderer 没有导入模型 SDK。
   - 确认 `vendor-runner` 的安全边界仍属于 `OPT-052`，不在本任务伪装完成。

## 2. 关键决定

1. 本任务只统一“调用编排”，不统一“协议内部实现”。
   - 原因：不同供应商的真实 API 差异很大，强行在本任务重写所有 adapter 会扩大范围。
2. 网关放在 main 侧 `src/main/services/model`。
   - 原因：renderer 不能接触 SDK、SQLite、API Key 和本地文件。
3. 任务中心写入仍由具体媒体调用的 `runWithTask` 负责。
   - 原因：文本调用很多是 Agent 流式对话，不都适合作为任务中心任务；后续 `OPT-032` 再统一取消、超时和落盘。
4. adapter VM timeout、fetch allowlist、日志长度截断不在本任务做。
   - 原因：这是 `OPT-052 自定义 adapter 安全边界`，提前混做会让边界不清。

## 3. 要做什么功能：怎么做

| 要做什么 | 怎么做 |
|---|---|
| 统一解析调用上下文 | 从 `modelKey` 解析真实 `vendorId:modelName`，读取 runtime 和 model，校验类型 |
| 标记协议类型 | 根据 vendor、内置定义、投影 adapter、ComfyUI id、Base URL 判断 `sdk/openai-compatible/adapter/workflow` |
| 文本调用统一 | `resolveTextRequest` 改为返回调用上下文，`invokeText/streamModelText` 通过网关执行 |
| 图片调用统一 | `generateImageByModel` 先解析上下文，再执行 imageRequest 和媒体结果校验 |
| 视频调用统一 | 在网关上下文内继续校验 video mode、参考素材数量、audio 支持 |
| TTS 调用统一 | `generateAudioByModel` 走同一上下文和失败归一 |
| 错误统一 | 网关 catch 非 `VtError` 后包装为 `MODEL_ERROR`，并带 `requestId` |
| 日志统一 | 开始、成功、失败写 `logger.detail`，终端不刷大段模型日志 |
| 验证统一 | 新增 `verify-opt-006-model-gateway.mjs` 并接入 `verify:core` |

## 4. 验收标准

1. 文本、图片、视频、TTS 都经过同一个模型调用网关。
2. 失败错误里能带 requestId，日志能用 requestId 定位。
3. renderer 不出现 `@ai-sdk/*`、`ai`、供应商 SDK import。
4. 内置供应商媒体能力未实现时仍明确失败，不假成功。
5. 普通连接投影仍能复用 adapter，不破坏 `OPT-053`。
6. `OPT-052/OPT-032/OPT-033` 未完成内容不会被误标完成。

## 6. 确认点

本任务没有需要停下来的确认点。执行口径采用前面已确认的原则：

1. 顶层响应仍是 `{ code, data, msg }`。
2. renderer 不直接碰 SDK、SQLite、文件系统。
3. 普通模型连接继续是主数据，vendor 投影是运行数据。
4. 多语言 UI 文案不在本任务新增页面，不涉及新增可见文案。
