## 0. 快速理解

```txt
一句话：把设置页剩下的开发者配置和关于页一次收口。
为什么现在做：M-002 只剩这两个尾项，继续拆开做会重复碰设置入口、IPC 和文案。
做完后有什么用：设置页能力闭环，后面可以直接进入应用壳批。
这一步不碰什么：不做静默更新，不做任意脚本执行，不在生产环境默认暴露危险工具。
```

## 1. 本批次做什么

```txt
目标：
  一次完成设置页剩余两项能力：
  1. 开发者配置
  2. 关于与版本信息

只做：
  1. DevTools / AI DevTools / localStorage 管理
  2. 版本显示、外链、手动检查更新、下载入口
  3. 设置页内统一入口和分区组织
  4. 对应 preload / ipc / main services 契约

不做：
  1. 任意脚本执行
  2. 静默安装或自动替换正在运行程序
  3. 启动时强制联网检查更新
  4. 生产环境默认暴露危险调试工具
```

## 2. 为什么要并批

```txt
1. 两个功能都在设置页开发者折叠区/信息区，属于同一层级。
2. 都要扩展 window.vtStudio.settings 下的新能力。
3. 都会碰 SettingsHome 结构、i18n 文案、受控外链/受控能力边界。
4. 单独做会重复写一遍设置页入口、IPC 注册、反馈和验证。
```

## 4. 本批次要做什么功能

### A. 开发者配置

```txt
1. 打开 DevTools。
2. 切换 AI DevTools 开关。
3. 管理 localStorage：搜索、复制、新增、编辑、删除、清空。
4. 对受保护 key 做脱敏和二次确认。
5. 生产环境默认隐藏危险能力。
```

### B. 关于与版本信息

```txt
1. 显示应用名、版本号、基础构建信息。
2. 打开 GitHub / Gitee / License 白名单外链。
3. 用户主动触发检查更新。
4. 选择更新源：GitHub / Gitee / 自定义 URL。
5. 下载新版本，但不静默安装。
```

### C. 批次内统一收口

```txt
1. 设置页结构：开发者区和关于区的落位要统一。
2. preload / ipc / service 命名统一挂在 settings 子域下。
3. 成功和失败反馈统一走现有 message 体系。
4. 危险能力都要明确“谁能用、什么时候能用、失败怎么提示”。
```

## 5. 当前代码现实和不合理点

```txt
1. SettingsHome 已有开发者折叠区，但没有独立开发者配置组件，结构不完整。
2. 当前没有 settings.dev 和 settings.about 的完整能力暴露。
3. F-002-014 已经明确了生产环境隐藏、清空 localStorage 强确认、禁止脚本执行；这是已确认事实，不再反复确认。
4. F-002-015 目前还是单任务视角，没有和应用壳里的 F-001-011 版本检查边界收口。
5. 关于页如果单独做“版本检查”，容易和应用壳版本入口重复；本批次需要先定口径。
```

专业结论：

```txt
1. 设置页里的“关于与版本信息”保留为详细入口。
2. 应用壳里的 F-001-011 只保留轻量入口或状态提示，详细检查和下载仍归 P1/F-002-015。
3. 开发者配置和关于页都属于受控工具区，不能当普通业务页随意暴露高风险能力。
```
