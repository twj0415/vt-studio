## 4. 当前代码现实和不合理点

当前实现已经有应用壳雏形，但和 M-001 目标有 5 个明显出入：

```txt
1. `WorkbenchLayout.vue` 当前把 projectMenus 直接常驻左侧导航，这和参考项目“项目内菜单在顶部、并且依赖 currentProject”冲突。
2. `router/index.ts` 当前把 settings 做成了独立路由页面，而不是统一设置弹窗入口。
3. `menu.ts` 当前 projectMenus 里包含导出，且没有 `novelOnly` 类控制字段，项目类型控制还没落。
4. `App.vue` 目前只包了一层 `t-config-provider`，没有应用初始化 loading、标题栏、受控外链、初始化失败兜底。
5. `WorkbenchLayout.vue` 当前顶部只显示标题和当前项目名，并没有真正的项目内顶部菜单。
```

专业结论：

```txt
1. 当前 layout 结构不能直接延伸，必须先把“左侧全局菜单”和“顶部项目菜单”拆开。
2. 设置页已经作为正式页面实现了 M-002，这和 M-001 的“统一设置弹窗入口”有产品结构冲突，P2 必须先定口径。
3. F-001-011 不能再做成一套独立检查更新链路；它只应承担轻量版本提示和打开 about 的入口，完整更新检查仍归 P1/F-002-015。
```

## 5. 本批次统一实现口径

### 5.1 导航结构口径

```txt
左侧只保留全局入口：
  项目管理
  任务中心
  设置入口
  辅助入口（反馈 / GitHub，未配置则隐藏）

顶部只保留项目内入口：
  小说/原文
  剧本 Agent

  顶部项目菜单不显示
```

### 5.2 设置入口口径

```txt
现实问题：
  M-002 已经实现成独立路由页 `settings`。

建议口径：
  第一版不强行回退成旧式 dialog。
  P2 里的 F-001-007/F-001-008 收口为“统一设置入口和统一设置菜单结构”，不再硬性要求必须是 dialog。
  也就是：保留“统一设置入口”这个业务语义，但实现形态允许继续使用独立设置页。
```

原因：

```txt
1. M-002 已经有大量实现和验证，强行改回 dialog 会产生纯结构性返工。
2. 设置统一入口这个业务语义没有丢；丢的是“表现形态必须是弹窗”。
3. 这个变化是实现形态偏差，不是业务能力缺失。
```
