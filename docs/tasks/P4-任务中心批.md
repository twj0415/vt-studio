## 1. 合并结论

P4 不再按单个 task 分开实现。

原因：

```txt
1. 任务列表、项目筛选、分类筛选、状态筛选、刷新、分页和失败原因都依赖同一个 task.list 查询链路。
2. 拆开实现会反复修改同一套 main service、IPC、preload 契约和任务中心页面。
3. CORE-006 已经完成任务表和任务写入底座，本批次应在现有底座上补可观测页面和对外契约。
```

## 4. 关键取舍

### 4.1 状态以 CORE-006 实现为准

当前 `src/main/services/task/constants.ts` 已有状态：

```txt
running
succeeded
failed
cancelled
```

单任务文档中提到的 `pending` 属于早期规划，但当前 CORE-006 没有落库和流转。P4 不临时新增 `pending`，避免任务状态模型扩大。

界面显示：

```txt
running -> 进行中
succeeded -> 已完成
failed -> 生成失败
cancelled -> 已取消
```

### 4.2 任务写入不暴露给 renderer

F-009-008 的目标是统一后续业务怎么写任务记录，不是让页面手动造任务。

本批次只确认：

```txt
业务服务 / 模型适配层 -> main task service -> tasks 表
renderer 任务中心 -> preload task.list/categoryOptions/projectOptions -> main service 只读查询
```

### 4.3 全部项目必须是真全部

项目筛选为空时，service 不加 `project_id` 条件。不能回退当前项目。

### 4.4 分类动态读取

分类来自 `tasks.category` 的现有数据，不写死枚举。

### 4.5 失败原因需要脱敏

失败原因写入时继续走 `normalizeUnknownError`。页面只展示 `errorReason`，无原因时显示兜底文案。
